# AI BILL INTELLIGENCE PLATFORM

## Master Product Requirements Document (PRD)

**Document Version:** 1.0
**Product Status:** New Product / MVP
**Document Purpose:** Master development specification for Antigravity
**Primary Target Market:** Pakistan initially, with architecture ready for international expansion
**Product Type:** AI-powered SaaS Web Application
**Primary Function:** Convert bills/invoices/receipts from images or PDFs into verified, structured, searchable financial data.

---

# 1. PRODUCT VISION

Build a modern AI-powered web application that allows a user to upload almost any printed bill, invoice, receipt, or purchase document and automatically:

1. Understand the document.
2. Identify the business/vendor.
3. Identify the customer when available.
4. Extract invoice/receipt information.
5. Extract line items.
6. Extract prices, quantities, taxes, discounts and totals.
7. Detect the document type.
8. Preserve the original document.
9. Assign confidence scores to extracted information.
10. Validate extracted information using business rules.
11. Highlight uncertain information.
12. Allow the user to review and correct the extracted data.
13. Store the verified information in a structured database.
14. Allow searching and filtering by date, business, customer, amount, category and other fields.
15. Generate weekly, monthly, yearly and custom reports.
16. Provide spending/business insights.
17. Eventually allow users to ask natural-language questions about their bills.

The system must NOT depend on fixed invoice templates.

Different businesses may have completely different invoice designs.

The AI must understand the semantic meaning of the document rather than relying on fixed screen coordinates or one template per business.

# 2. CORE PRODUCT PRINCIPLE

The fundamental product workflow is:

UPLOAD → UNDERSTAND → EXTRACT → VALIDATE → VERIFY → STORE → SEARCH → ANALYZE

The product must prioritize:

* Accuracy
* Transparency
* User trust
* Data integrity
* Security
* Simplicity
* Extensibility
* Performance

The system must never silently invent information.

If information does not exist on the document, the value must remain null/unknown.

Example:

Correct:

Customer Phone: Not Found

Incorrect:

Customer Phone: 03001234567

when that number was not present on the document.

# 7. DYNAMIC DOCUMENT MODEL

The system must NOT require every invoice to contain the same fields.

Example:

A restaurant bill may contain:

* Table
* Waiter
* Service charge

A pharmacy invoice may contain:

* Medicine
* Batch
* Expiry
* Doctor
* Patient

An electronics invoice may contain:

* Serial number
* Warranty
* Model number

Therefore use:

## Standard fields

For common invoice information.

AND

## Dynamic/custom fields

For document-specific information.

Example:

```json
{
  "custom_fields": {
    "doctor": "Dr. Ahmed",
    "patient": "Muhammad Ali",
    "batch_number": "B12345",
    "expiry_date": "2027-04"
  }
}
```

Do not alter the database schema every time a new document type appears.


# 12. CONFIDENCE SYSTEM

Every AI-extracted field should have a confidence value where technically possible.

Example:

```text
Business Name      99%
Invoice Date       98%
Invoice Number     97%
Customer Name      72%
Phone Number       51%
Total              99%
```

Confidence levels:

### High

90–100%

### Medium

70–89%

### Low

0–69%

These thresholds must be configurable.

Do not treat confidence as absolute truth.

A field can have high AI confidence but still fail a business-rule validation.

---

# 13. VERIFICATION SYSTEM

The system should identify fields requiring user attention.

Example:

```text

Invoice Date       ✓
Invoice Number     ✓
Total              ✓
Tax                ⚠
Customer Name      ⚠
```

The user should be able to:

* Edit
* Accept
* Ignore
* Mark as unavailable

Do not force users to fill information that does not exist.

---

# 14. VALIDATION ENGINE

After AI extraction, run deterministic validation.

Examples:

### Quantity calculation

```text
quantity × unit_price ≈ line_total
```

### Invoice calculation

```text
subtotal
- discount
+ tax
+ additional charges
≈ total
```

### Item count

If 5 line items were extracted:

```text
item_count = 5
```

### Date validation

Date should be a valid date.

### Currency validation

Currency should be normalized.

### Negative values

Unexpected negative totals should trigger review.

### Duplicate detection

Compare:

* Vendor
* Invoice number
* Date
* Total
* File hash

and flag possible duplicates.

The system must NOT automatically delete suspected duplicates.

# 43. DO NOT INVENT DATA

This is a hard requirement.

The AI must not:

* Guess a phone number
* Guess a customer
* Guess a missing invoice number
* Guess a tax amount
* Guess an item price
* Guess a date
* Infer a value as fact when it is not present

Use:

```text
null
```

when unavailable.

---

# 44. AI PROMPTING PRINCIPLES

Extraction prompts should explicitly instruct the model:

1. Extract only information present in the document.
2. Do not invent missing values.
3. Preserve line-item relationships.
4. Distinguish subtotal from total.
5. Distinguish tax from discount.
6. Preserve currency.
7. Return null when information is absent.
8. Return confidence.
9. Return evidence where available.
10. Follow the defined JSON schema strictly.

Prompts must be version-controlled.
